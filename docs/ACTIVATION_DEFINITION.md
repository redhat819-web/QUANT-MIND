| 반복 | household마다 **처음 한 번만** 분자에 셈. 이후 조회는 Retention에서 다룸 | 결정 필요: 최초 시각 기록 위치(아래) |
| 내부 테스트 | mock 모드, 개발·점검 계정, `[통합테스트]`·`[점검]` 데이터, e2e 실행은 분자·분모에서 제외 | 결정 필요: 내부 계정 구분 방법(예: 계정 플래그) |
| 진행 중 코호트 | t0 + 168시간이 집계 시점보다 뒤인 household는 분자·분모에서 빼고 "관찰 중"으로 따로 표시 | 정의 |
| 7일 안에 탈퇴·삭제 | household가 삭제돼도(002 FR-015) 분모에서 빠지면 안 됨 | **결정 필요**: 식별자 없는 익명 집계 기록을 남길지 |

**최초 시각 기록 위치 (결정 필요):** 분석 이벤트에는 household 식별자를 넣을 수 없다(002 FR-021).
그래서 household 단위 분자는 분석 도구로 셀 수 없다. 서비스 DB에 "유효한 부부 합계를 처음 본 시각"을
남기고 서버에서 집계하는 방식을 제안한다(002 FR-022).

## 3. Activation Rate 계산식

```
Activation Rate (%) =
  t0부터 168시간 안에 유효한 부부 합계(조건 ①~⑤)를 처음 본 household 수
  ÷ 관찰 기간이 끝난 코호트에서 새로 생성된 household 수 (내부·테스트 제외)
  × 100
```

**현재 실제 Activation Rate: 미측정.** 근거는 다음과 같다.
- 002 기능(가입, 초대, 업로드)이 구현되지 않았다.
- 생성 시각 컬럼과 최초 조회 기록이 없다.
- 분석 태그가 연결되어 있지 않다.
- 기존 household는 1개뿐이고 코호트 대상도 아니다.

## 4. 유효하지 않은 상태의 조회를 성공으로 세면 안 되는 이유

- **0원 화면은 가치가 아니다.** 배우자가 없거나 데이터가 반영되지 않아도 대시보드는 정상으로 열리고
  "상대방 0원"을 보여준다. 이를 성공으로 세면 혼자 가입해 화면만 연 household까지 활성화로 잡힌다.
  그러면 첫 가설("배우자도 합류하는가")을 정반대로 읽게 된다.
- **page_view는 화면이 떴다는 뜻일 뿐이다.** 가입 직후 `/` → `/dashboard` 자동 이동(`src/app/routes.tsx`)만으로도
  생긴다.
- **업로드 버튼 클릭도 같다.** 검증에 실패한 파일은 아무것도 반영하지 않는다(002 FR-011). 클릭을 세면
  반영되지 않은 시도까지 성공이 된다.
- 결론: 성공은 "유효한 상태에서 결과를 본 것"으로 한정한다. 가입 완료, page_view, 버튼 클릭은 앞 단계
  퍼널 지표로만 쓴다.

## 5. 첫 가치 검증 인터뷰 질문

모두 지난 경험을 묻는다. 활성화 조건을 충족한 것과 실제로 도움이 된 것은 다를 수 있으므로 따로 확인한다.

1. "가장 최근에 부부 합계 화면을 본 날을 떠올려 주세요. 그 화면을 열기 직전에 무엇을 하고 계셨고, 본 뒤에
   실제로 하신 일은 무엇이었나요?"
2. "이 서비스를 쓰기 전에 두 분의 자산을 합쳐 본 마지막 때는 언제였나요? 그때 어떤 방법을 썼고 얼마나
   걸렸나요?"
3. "합계를 본 뒤 배우자분과 그 숫자로 이야기를 나눈 적이 있나요? 가장 최근 대화는 무엇이었고, 그 뒤에
   결정하거나 바꾼 것이 있었나요?"

## 6. 002 plan으로 넘길 일

- `household` 생성 시각, `household_members` 합류 시각 컬럼 추가
- 유효한 부부 합계를 처음 본 시각을 서비스 DB에 기록
- 내부·테스트 계정 구분 방법
- household 삭제 후에도 남길 익명 집계 기록 여부
- `hasSyncFailure` 상태를 성공으로 칠지 여부
