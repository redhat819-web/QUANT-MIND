- 방법: 코드·spec을 읽고 정리함. 실제 방문·행동 데이터는 없으며, 모든 집계값은 **미측정**.

  `specs/001-quant-mind-dashboard/spec.md`.

## 1. 분석 단위: household

부부 합계와 합의는 두 사람이 모두 들어와 있어야 생기는 가치다. 한 사람만 가입한 상태는 개인
자산 조회 앱과 같다. 그래서 지표의 기본 단위는 사용자가 아니라 household로 둔다. DB는 이미
`household_id`와 `is_household_member()` RLS로 여러 household를 분리할 수 있다.

## 2. AARRR 측정표

| 단계 | 지표·단위 | 분자 | 분모 | 기간 | 현재 상태 | 필요한 데이터 |
|---|---|---|---|---|---|---|
| Acquisition | 가입 전환율 (%) | `signup_complete` 세션 수 | 랜딩 page_view 세션 수 | 주, 채널(UTM)별 | 현재 측정 대상 없음 (랜딩·가입 없음) | 랜딩, 가입 화면, GA4 기본 태그, 커스텀 이벤트 |
| Activation (1차) | 부부 연결 완료율 (%) | 7일 안에 배우자 초대 수락과 두 사람 데이터 연결을 모두 마친 household 수 | 생성된 household 수 | household 생성일 + 7일 | 현재 측정 대상 없음 (초대·연결 화면 없음) | 초대·수락, 데이터 연결 이벤트, DB 집계 |
| Activation (2차) | 첫 합의 도달률 (%) | 첫 합의 확정까지 간 household 수 | 1차 활성화 household 수 | 활성화일 + 30일 | 코드에서 행동 조건만 확인 (`agreement_record`) | DB 집계 |
| Retention | 주간 공동 활성 household 비율 (%) | 해당 주에 두 사람이 모두 저장 성공 행동을 한 household 수 | 가입 주 코호트의 household 수 | 가입 주 기준 코호트, 주 단위 | 현재 측정 대상 없음 | 저장 성공 이벤트, DB 집계 |
| Referral | 추천 가입률 (%) | 추천 링크로 가입한 household 수 | 추천 링크를 보낸 household 수 | 발송일 + 30일 | 현재 측정 대상 없음 (추천 기능 없음) | 추천 링크·가입 이벤트 |
| Revenue | 유료 전환율 (%), 월 반복 매출 (원) | 유료 전환 household 수 | 체험이 끝난 household 수 | 월 단위 | 현재 측정 대상 없음 (결제 없음) | 결제 시스템 기록 |

- 배우자 초대는 Activation이다. Referral(다른 부부에게 권하기)과 섞지 않는다.
- 사용자의 자산 평가금액·수익률은 매출이 아니다. 분석 이벤트로 보내지도 않는다.
- page_view는 화면이 떴다는 뜻일 뿐, 숫자를 확인했다는 뜻이 아니다.
- 첫 번째로 확인할 가설: "한 사람이 가입하면 배우자도 들어오는가". 그래서 첫 측정 대상은 초대
  수락률이다. 여기서 막히면 뒤의 지표는 의미가 없다.

## 3. 최소 이벤트 정의표

상용화 화면은 아직 없으므로, 코드 위치는 "예정"으로 적는다. 모든 이벤트는 저장·처리 성공 시점에
보낸다. 공통 허용 속성은 `data_source`('mock' | 'supabase')다.

| 이벤트 | 발생 조건 | 코드 위치 | 허용 속성 | 미발생 조건 |
|---|---|---|---|---|
| `signup_complete` | 계정 생성 성공 | 예정: 가입 화면 | `method`('email' 등) | 입력 검증 실패, 중복 이메일 |
| `household_create_success` | household 생성 성공 | 예정: 온보딩 | 없음 | 생성 요청만 보낸 시점 |
| `partner_invite_send` | 초대 생성·발송 성공 | 예정: 온보딩 | `channel`('link' \| 'email') | 초대 버튼 클릭만 한 경우 |
| `partner_invite_accept` | 배우자가 household에 합류 성공 | 예정: 초대 수락 화면 | 없음 | 초대 링크 열기만 한 경우, 만료 초대 |
| `data_connect_success` | 자산 데이터 원본 연결 성공 | 예정: 데이터 연결 화면 | `source_type`('sheet' \| 'institution' 등) | 연결 시도, 인증 실패 |
| `first_sync_success` | household의 첫 동기화 반영 성공 | 예정: 동기화 처리부 | 없음 | 두 번째 이후 동기화 |
| `agenda_save_success` 외 판단 로그 이벤트 | 현재 구조 측정 계획과 같음 | `src/pages/JudgmentLogPage.tsx` 등 | 현재 계획과 같음 | 현재 계획과 같음 |
| `trial_start` | 무료 체험 시작 성공 | 예정: 결제 화면 | `plan` | 플랜 화면 보기만 한 경우 |
| `subscription_start` | 첫 결제 승인 | 예정: 결제 처리부 | `plan` | 결제 시도, 승인 실패 |

**보내지 않는 값:** 금액·수익률·비중·종목명·계좌, 안건·의견·사유 본문, 이메일, user ID,
household ID, 이름, 날짜, 국가·지역 커스텀 속성.

**수집 경로 분리:**
- GA4: 랜딩, 가입, 결제 같은 웹 유입 흐름.
- 서버 DB 집계: household 단위 활성화·리텐션. 개별 식별자를 밖으로 보내지 않고 집계값만 쓴다.

## 4. 지금은 계산할 수 없는 지표

1. 위 AARRR 지표 전부: 해당 화면·이벤트·태그가 없음.
2. household 단위 리텐션을 GA4만으로 계산하는 것: household ID를 보내지 않는 원칙과 충돌.
3. 화면 밖에서 이루어진 논의, 숫자를 실제로 읽었는지 여부: 이벤트로 알 수 없음.

## 5. 상용화 전에 바꿔야 할 제품·구조

1. **데이터 수집 방식.** 지금은 Apps Script가 service role key로 Supabase에 쓴다. 이 키는 고객에게
   나눠줄 수 없다(AGENTS.md 규칙). 서버 쪽 수집 API나 금융기관 연동이 필요하다.
2. **가입, household 생성, 배우자 초대, 탈퇴.** 한 사람이 household를 떠날 때 상대방이 보던 데이터와
   합의 기록을 어떻게 처리할지 정해야 한다.
3. **배포.** 실서비스용 호스팅과 환경 분리. 그 전까지 deploy.yml의 mock 강제 검사는 유지한다.
4. **앱 안에서 분류 변경·미매핑 종목 매핑(T057).** 시트를 모르는 사용자도 고칠 수 있어야 한다.

## 6. 결정되지 않은 조건과 확인이 필요한 위험

법률 판단은 전문가 검토가 필요하다. 아래는 확인할 쟁점 목록이다.

| 항목 | 정할 것 |
|---|---|
| 분석 동의 | 분석 도구 동의 절차, 거부 시 이벤트를 보내지 않는 동작. 동의자만 모수가 됨 |
| 국외 이전 | GA4 등 국외 서버 전송에 대한 고지·동의 |
| 배우자 데이터 | 상대방에게 내 자산이 보이는 것에 대한 각자의 동의 |
| 금융기관 연동 | 마이데이터 방식이라면 허가·제휴 요건 |
| 투자 조언 경계 | "참고용" 고지(FR-008) 유지. 분석·시나리오 기능을 붙일 때 유사투자자문 해당 여부 |
| 사용자 식별 | household 단위 집계를 서버에서만 할지, 가명 식별자를 분석 도구로 보낼지 |
| 내부 테스트 제외 | 개발·점검 계정, e2e 실행, `[통합테스트]`·`[점검]` 데이터, mock 모드 제외 기준 |
| 기간·표본 | 활성화 기준 일수(7일·30일 제안값) 확정, 초기 표본이 작을 때 건수로 볼지 비율로 볼지 |
| 보관 기간 | 분석 데이터 보존 기간 |

## 7. 진행 순서

1. 대상과 가치 가설, 결제 모델을 정한다.
2. 새 feature spec(`002-…`)으로 가입, household 초대, 데이터 수집, 동의를 정의한다.
3. 그 spec의 화면에 맞춰 이 측정 계획의 "예정" 위치를 확정한다.
4. 실서비스 환경과 동의 화면이 생긴 뒤에 분석 태그를 붙인다.
